# ADR-005: Error Handling Boundaries and Validation Strategy

## Status
Accepted

## Context
The issue or problem driving this decision. Include:
- Technical constraints (in-memory only, standard library, backward compatibility)
- User experience requirements (intuitive CLI, zero breaking changes)
- Specific challenge this decision resolves

The Todo In-Memory Python Console App needs a consistent error handling strategy that validates user input, handles edge cases, and provides clear error messages while maintaining the required format "[ERROR] Description". The system must determine where validation occurs (CLI parser vs. core CRUD vs. feature modules) and ensure consistent error message formatting across all components. This is critical for user experience and to satisfy the constitution's requirement for user-friendly error messages.

## Decision
The chosen approach. Be precise:
- NOT "use argparse" but "Use argparse.ArgumentParser with subparsers for commands, custom type validators for priority/tag normalization"
- NOT "separate modules" but "Core CRUD in /src/core/crud.py with pure data operations; CLI concerns isolated in /src/cli/parser.py; query logic in /src/features/query.py with dependency injection pattern"

Implement a layered validation approach with validation occurring at multiple boundaries: 1) CLI parser performs basic input validation (required arguments, valid flag values), 2) Core CRUD operations perform data model validation (valid priority values, tag format), 3) Feature modules perform business logic validation (valid filter combinations). Use a centralized error formatting function to ensure all errors follow the "[ERROR] Description" format. Implement exception handling at each layer with appropriate error wrapping to maintain context while providing user-friendly messages.

## Alternatives Considered
List 2-3 rejected approaches with concise rejection rationale:
- Alternative A: [Description] → Rejected because [specific constraint violation or UX drawback]
- Alternative B: [Description] → Rejected because [maintenance burden or backward compatibility risk]

- Centralized validation in one location: Would create a bottleneck and make the system harder to maintain and extend.
- No validation in CLI layer: Would allow invalid data to propagate deeper into the system, making error handling more complex.

## Consequences
### Positive
- Enables [specific capability]
- Preserves [backward compatibility guarantee]
- Simplifies [future phase migration]

Enables consistent error handling across all components of the application. Preserves the required error message format across all modules. Simplifies debugging by providing clear error context at appropriate layers.

### Negative / Trade-offs
- Increases [complexity in specific area]
- Requires [additional validation layer]
- Limits [future flexibility in X area]

Increases complexity with validation logic distributed across multiple layers. Requires additional validation functions and error handling code. Limits flexibility to change error handling approach without affecting multiple components.

## Validation Criteria
How we verify this decision works correctly:
- Test case: [Concrete example demonstrating decision correctness]
- Boundary condition: [Edge case that would break poor implementation]

Test case: Command "add 'Task' 'Description' --priority invalid" should result in an error message "[ERROR] Invalid priority: 'invalid'. Must be high/medium/low". Boundary condition: Invalid task IDs in update operations should result in appropriate error messages without crashing the application.
