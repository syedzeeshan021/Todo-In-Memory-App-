# ADR-003: Query Execution Pipeline for Combined Filters/Sort/Search

## Status
Accepted

## Context
The issue or problem driving this decision. Include:
- Technical constraints (in-memory only, standard library, backward compatibility)
- User experience requirements (intuitive CLI, zero breaking changes)
- Specific challenge this decision resolves

The Todo In-Memory Python Console App needs to implement a query execution pipeline that handles combined filters (status, priority, tags), search (keyword matching), and sort operations (by created date, priority, or title) with predictable behavior and acceptable performance. The pipeline must process multiple operations efficiently in memory while maintaining performance requirements (operations complete in <100ms with 1000 tasks). The solution must handle complex combinations like "search 'meeting' --status pending --priority high --tag work --sort title" while ensuring consistent results regardless of parameter order.

## Decision
The chosen approach. Be precise:
- NOT "use argparse" but "Use argparse.ArgumentParser with subparsers for commands, custom type validators for priority/tag normalization"
- NOT "separate modules" but "Core CRUD in /src/core/crud.py with pure data operations; CLI concerns isolated in /src/cli/parser.py; query logic in /src/features/query.py with dependency injection pattern"

Implement a query execution pipeline with the following order of operations: 1) Apply filters (status, priority, tags) to reduce the dataset, 2) Apply search keyword matching to the filtered results, 3) Apply sorting to the final result set. This approach minimizes the amount of data processed at each stage, optimizing performance. Use Python's built-in `filter()`, `sorted()`, and list comprehension functions for efficient in-memory operations. Implement the pipeline in the /src/features/query.py module with clear separation from core CRUD operations.

## Alternatives Considered
List 2-3 rejected approaches with concise rejection rationale:
- Alternative A: [Description] → Rejected because [specific constraint violation or UX drawback]
- Alternative B: [Description] → Rejected because [maintenance burden or backward compatibility risk]

- Different order of operations (e.g., sort first, then filter): Would be less efficient as it would sort a larger dataset before filtering.
- Separate pipelines for each operation: Would not properly handle interactions between operations and could lead to inconsistent results.

## Consequences
### Positive
- Enables [specific capability]
- Preserves [backward compatibility guarantee]
- Simplifies [future phase migration]

Enables complex query combinations with predictable and efficient behavior. Preserves performance requirements by minimizing data processing at each stage. Simplifies debugging and testing by having a consistent execution order.

### Negative / Trade-offs
- Increases [complexity in specific area]
- Requires [additional validation layer]
- Limits [future flexibility in X area]

Increases complexity in the query logic with multi-stage processing. Requires additional validation to ensure proper parameter combinations. Limits flexibility to optimize individual operations separately without considering the pipeline as a whole.

## Validation Criteria
How we verify this decision works correctly:
- Test case: [Concrete example demonstrating decision correctness]
- Boundary condition: [Edge case that would break poor implementation]

Test case: Command "list --status pending --priority high --tag work --sort title" should filter by status, then priority, then tags, and finally sort the results by title. Boundary condition: When no tasks match the filters, the pipeline should return an empty result set without errors.
