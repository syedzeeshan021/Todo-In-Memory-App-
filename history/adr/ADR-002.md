# ADR-002: Task Model Evolution with Priority and Tags

## Status
Accepted

## Context
The issue or problem driving this decision. Include:
- Technical constraints (in-memory only, standard library, backward compatibility)
- User experience requirements (intuitive CLI, zero breaking changes)
- Specific challenge this decision resolves

The Todo In-Memory Python Console App needs to enhance the basic Task model with priority and tags functionality while maintaining 100% backward compatibility with existing CRUD interfaces. The enhanced model must support new fields (priority, tags) without breaking existing functionality, preserve existing data structures for basic operations, and maintain performance requirements with up to 1000 tasks in memory. The solution must use only Python standard library components as per project constraints.

## Decision
The chosen approach. Be precise:
- NOT "use argparse" but "Use argparse.ArgumentParser with subparsers for commands, custom type validators for priority/tag normalization"
- NOT "separate modules" but "Core CRUD in /src/core/crud.py with pure data operations; CLI concerns isolated in /src/cli/parser.py; query logic in /src/features/query.py with dependency injection pattern"

Enhance the Task model by adding priority (str) and tags (list[str]) fields with appropriate defaults ("medium" for priority, [] for tags). Maintain all existing fields (id, title, description, completed, created_at, updated_at) and preserve the same CRUD interface methods. Implement field validation and normalization in the model layer to ensure data consistency. Store the enhanced Task objects in the same in-memory data structures (lists/dictionaries) to maintain performance characteristics.

## Alternatives Considered
List 2-3 rejected approaches with concise rejection rationale:
- Alternative A: [Description] → Rejected because [specific constraint violation or UX drawback]
- Alternative B: [Description] → Rejected because [maintenance burden or backward compatibility risk]

- Separate task models for basic and enhanced functionality: Would increase complexity and make it harder to maintain consistency between basic and enhanced tasks.
- Database or file-based storage: Would violate the "in-memory only" constraint specified in the project requirements.

## Consequences
### Positive
- Enables [specific capability]
- Preserves [backward compatibility guarantee]
- Simplifies [future phase migration]

Enables rich task management with priorities and tags while maintaining the same interface for basic operations. Preserves backward compatibility by keeping all existing fields and methods unchanged. Simplifies migration to future phases by maintaining a consistent data model structure.

### Negative / Trade-offs
- Increases [complexity in specific area]
- Requires [additional validation layer]
- Limits [future flexibility in X area]

Increases complexity in the data model with additional fields and validation requirements. Requires additional validation layers to handle priority and tag constraints. Limits flexibility to change the core data structure without affecting all parts of the system that use Task objects.

## Validation Criteria
How we verify this decision works correctly:
- Test case: [Concrete example demonstrating decision correctness]
- Boundary condition: [Edge case that would break poor implementation]

Test case: Creating a basic task without priority/tags should work identically to the original implementation with default values applied. Creating an enhanced task with priority and tags should work with new functionality. Boundary condition: Attempting to create a task with invalid priority should be properly rejected with appropriate error messages.
