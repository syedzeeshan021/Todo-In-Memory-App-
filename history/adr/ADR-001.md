# ADR-001: CLI Parsing Strategy for Extended Commands

## Status
Accepted

## Context
The issue or problem driving this decision. Include:
- Technical constraints (in-memory only, standard library, backward compatibility)
- User experience requirements (intuitive CLI, zero breaking changes)
- Specific challenge this decision resolves

The Todo In-Memory Python Console App needs to extend basic commands with optional flags (e.g., --priority, --tag, --sort) while preserving the original command syntax for backward compatibility. The CLI must support both basic commands (add "title" "desc") and extended commands (add "title" "desc" --priority high --tag work) without breaking existing functionality. The solution must use only Python standard library components as per project constraints.

## Decision
The chosen approach. Be precise:
- NOT "use argparse" but "Use argparse.ArgumentParser with subparsers for commands, custom type validators for priority/tag normalization"
- NOT "separate modules" but "Core CRUD in /src/core/crud.py with pure data operations; CLI concerns isolated in /src/cli/parser.py; query logic in /src/features/query.py with dependency injection pattern"

Use Python's built-in `argparse` module with subparsers to handle different commands (add, list, search, update, etc.) and optional arguments. Configure the parser to support both positional arguments and optional flags while maintaining backward compatibility with existing command syntax. Implement custom type validators for priority normalization (case-insensitive conversion to lowercase) and tag parsing (comma-separated string to list conversion with whitespace trimming).

## Alternatives Considered
List 2-3 rejected approaches with concise rejection rationale:
- Alternative A: [Description] → Rejected because [specific constraint violation or UX drawback]
- Alternative B: [Description] → Rejected because [maintenance burden or backward compatibility risk]

- Custom parsing with sys.argv: Would require more manual work and error handling, increasing the likelihood of bugs and inconsistencies in argument processing.
- Third-party libraries like click: Would violate the "standard library only" constraint specified in the project requirements.

## Consequences
### Positive
- Enables [specific capability]
- Preserves [backward compatibility guarantee]
- Simplifies [future phase migration]

Enables flexible command syntax supporting both basic and extended functionality without breaking existing commands. Preserves backward compatibility by allowing the same command structure as the basic version. Simplifies testing and maintenance by using a well-documented standard library solution.

### Negative / Trade-offs
- Increases [complexity in specific area]
- Requires [additional validation layer]
- Limits [future flexibility in X area]

Increases complexity in argument parsing logic compared to simpler positional-only arguments. Requires additional validation layers to handle the optional flags and their interactions. Limits flexibility to change argument parsing approach without affecting the entire CLI interface.

## Validation Criteria
How we verify this decision works correctly:
- Test case: [Concrete example demonstrating decision correctness]
- Boundary condition: [Edge case that would break poor implementation]

Test case: Basic command "add 'Title' 'Description'" should work identically to the original implementation. Extended command "add 'Title' 'Description' --priority high --tag work,urgent" should work with new functionality. Boundary condition: Commands with invalid priority values should be properly rejected with appropriate error messages.
